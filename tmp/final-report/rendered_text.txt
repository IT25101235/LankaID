Introduction 
Project overview 
LankaID is a Java web application for managing National Identity Card (NIC) and passport services in 
one portal. Citizens can register, submit a new application or request renewal or replacement, upload 
supporting evidence, follow officer feedback, pay a simulated fee and book a biometric appointment. 
Staff review applications, record centre attendance and biometric completion, prepare an issuance 
register, and manage delivery or collection. 
The five-member team developed the prototype for SE2030 Software Engineering. Requirements 
analysis, UML modelling, iterative development, object-oriented implementation and testing support a 
connected citizen-service workflow [1], [2]. Payments, biometric device capture and physical document 
production remain simulations; the portal records their workflow outcomes. 
Problem and objectives 
The project addresses fragmented application handling: paper-based evidence, repeated visits, separate 
staff records and limited visibility of application progress. A shared portal can reduce repeated data entry 
and expose the next action to the applicant and responsible officer. These benefits are design goals; 
processing-time savings have not been measured in a government deployment. 
The objectives are to provide online applications with saved drafts; make review decisions traceable; 
enforce appointment capacity and change rules; present progress and notifications; support assisted walk-
in services; and give administrators and the director operational oversight. The implementation connects 
these goals through one database and controlled status changes. 
Users and stakeholders 
User or stakeholder Purpose and access 
Citizen Applies, corrects evidence, pays, books, tracks and chooses delivery or collection.  
NIC and passport officers Review their assigned document type, manage appointment slots, check in citizens 
and record biometric completion. 
CSR and walk-in visitor CSR handles support, assisted visits and collection. A visitor uses the walk -in route 
with mobile verification. 
Director and administrator Director handles referrals, reports and issuance registers. Administrator manages 
accounts, centres, fees, notices and maintenance. 
Scope and boundaries 
The prototype covers registration through recorded handover for new, renewed and replaced documents. 
It assumes internet access, an English-language browser interface and configured SQL Server. It does not 
connect to live government identity records, a certified payment gateway, biometric hardware, courier 
tracking or physical printing. Uploaded files use local server storage.

Supporting requirements and data rules 
Email/SMS delivery, password recovery, file preview, QR generation, notification read state and shared 
navigation support the major functions. Common work was shared across the group. References, 
ownership links and workflow status must remain consistent between screens and persisted records. 
Appointments identify their service type and centre. Active booking counts include confirmed, checked-in 
and completed bookings; cancellation releases capacity. The server checks ownership and current state 
when a citizen changes a booking. Stale confirmations are rejected instead of overwriting a newer 
booking. 
Priority and completion boundaries 
The design backlog contains 31 stories: 20 high, 10 medium and one low priority [2]. Core portal 
workflows are implemented. Activity monitoring is represented by domain audit records and operational 
views; a general log browser is outside the delivered interface. These boundaries appear again in the 
implementation and future-work sections.

Constraints and assumptions 
The application is Java-based and developed within a semester [1]. The build declares Spring Boot 4.1.0 
and Java 17; SQL Server and its schema must be configured before startup. Hibernate validates the 
schema rather than creating production tables automatically. Version-specific setup must be checked 
before demonstration. 
Email verification needs configured SMTP credentials and network access. SMS uses an HTTP phone 
gateway whose availability depends on the local network/device. Webcam scanning needs camera 
permission and a suitable browser origin. Credentials belong in environment configuration and must not 
appear in report screenshots. 
Appointment policies use Sri Lanka time. The simulated payment/capture stages demonstrate business 
flows but do not establish banking settlement, legal identity verification or actual biometric collection. An 
approved prototype application is not an official identity document.

Architecture and design patterns 
LankaID is a layered monolith. A browser request reaches a Spring MVC controller, which checks 
session/role context and calls a service. Services hold business rules/transaction boundaries; repositories 
persist entities to SQL Server. Thymeleaf renders the model. OTP adapters, local file storage, QR 
generation and notification publishing connect to this flow. 
Pattern or separation Example and benefit 
MVC / service layer AppointmentController delegates to AppointmentService, separating presentation and 
business decisions. 
Repository AppointmentRepository defines persistent lookup and locking without database access in 
templates. 
Observer NotificationPublisher sends an event to InAppNotificationObserver, reducing 
module/storage coupling. 
Adapter / policy object SmsSender isolates delivery; BookingChangePolicy centralises time/status rules for pages 
and server checks.

Recorded results and remaining findings 
Stored Surefire XML reports contain 295 executed cases across 63 report files: 293 passed, two failed, 
zero errors and zero skipped. These historical files can span different runs; they do not establish a fresh 
full-suite result against the final submission. 
Both failures are in MarickarVerificationTestCases. One expects HTTP 403 for an unauthorised CSR 
request but records HTTP 404; the other expects an official-notification email call that was not observed. 
Expected behaviour must be reconciled with current routes/notification integration, followed by a clean 
regression run before claiming that every test passes. 
Ethical and operational considerations 
Identity evidence is sensitive. Access checks, limited QR payloads, hashes and traceable decisions 
support privacy/accountability. A human officer makes decisions; the assistant provides public guidance. 
Assisted visits reduce exclusion. Deployment needs a retention policy, encrypted storage and formal 
security/accessibility/performance checks. OWASP ASVS provides a security-review reference [17].

Conclusion and Future Work 
Summary of achievements 
LankaID connects the main stages of an identity-service request in one academic prototype. Citizens have 
verified registration, drafts/evidence, tracked reviews, simulated payment, appointment passes and 
delivery/collection records. Officers have document-specific queues and centre operations; CSR provides 
assisted service; the director manages referrals/issuance records; the administrator maintains operating 
settings. 
The main outcome is a connected workflow with explicit responsibilities and controlled states. UML, 
relational design, layered Java code and automated checks link software-engineering activities to 
delivered screens. Live payments, government-data integration, biometric devices and physical 
production remain outside the prototype scope. 
Challenges and responses 
Challenge Response and remaining lesson 
Database drift Schema validation exposed mismatches. Shared schema/migration scripts improved 
setup; versioned migrations would improve upgrades. 
Concurrent/stale booking Row locks, booking versions and a shared policy protect capacity/changes. Boundary 
cases must stay in regression checks. 
Module integration Shared statuses, navigation and theme connected independently developed screens. 
Earlier contracts would reduce rework. 
External dependencies Gateway interfaces and mocks limit coupling. Demonstration still requires verified 
SMTP/SMS configuration. 
Regression evidence Historical results record two failed assertions. A clean dated rerun is needed before 
claiming a fully passing final suite. 
Prioritised future work 
First, resolve regression findings, standardise migrations and complete a security review with framework-
level CSRF protection and encrypted evidence storage. Document retention/consent procedures and verify 
every role/owner boundary before deployment. 
Next, integrate certified payment, authorised government-data interfaces, biometric devices and 
delivery/printing services with recovery/audit checks. Then add Sinhala/Tamil, perform 
accessibility/usability studies, introduce reminders and load-test paginated staff lists. Measured outcomes 
should guide scaling decisions.

Teamwork and improvement 
The strongest shared result was the module connection: citizen submission feeds review, approval feeds 
payment/booking, biometric completion feeds issuance, and issuance feeds delivery. Agreement on 
records, status names and transition ownership made those handoffs possible. Shared navigation/theme 
made them easier to follow. 
Coordination can improve through versioned migrations, common response/notification contracts and 
regression results regenerated for the exact submission. Planned effort should remain separate from 
completion dates so schedule problems stay visible. 
Future work should pair a named feature owner with an agreed acceptance flow and another member 
checking the handoff. Regular integration checks are easier to diagnose than a late combined failure. 
Personal module knowledge and understanding of the full lifecycle are both necessary for the 
demonstration and viva.
