P11 [Heading 1] Introduction
P12 [Heading 2] Project Overview
P13 [Normal] Web Based Identity Issuing Service (branded LankaID) is a Java web application that brings the issuing of Sri Lankan National Identity Cards (NIC) and passports online. A citizen registers, applies for a new document or asks for a renewal or lost-document replacement, uploads supporting evidence, pays the fee, books a biometric appointment at a service centre, tracks progress and finally receives the document by home delivery or collects it from a centre. Officers review each application, record the biometric visit, and the Identity Service Director issues approved documents in printing batches. Customer service representatives help visitors who cannot use the portal, and a system administrator maintains staff accounts, service centres and system settings.
P14 [Normal] The system was built by a five-member group for the SE2030 Software Engineering module [1] using Spring Boot, Thymeleaf and Microsoft SQL Server. It is an academic prototype: card payments, biometric hardware capture and card production are simulated, while registration, verification, scheduling, notifications and reporting are fully working.
P15 [Heading 2] Problem Background
P16 [Normal] Obtaining or renewing an identity document normally means several visits to a government office, paper forms and photocopies, long queues and weeks of waiting without any information about progress. Paper files can be lost or altered, and each office keeps its own records. LankaID replaces this with one portal in which every step is recorded, every decision has an author and a time, and the only mandatory physical visit is the biometric appointment.
P17 [Heading 2] Objectives
P18 [List Paragraph] Let citizens apply for, renew or replace an NIC or passport online, with saved drafts, document uploads and a visible status timeline.
P19 [List Paragraph] Give NIC and passport officers separate, role-restricted queues in which they can approve, reject with a reason, or request corrections.
P20 [List Paragraph] Manage biometric capacity fairly: officers publish capacity-limited slots, citizens book them, and the system prevents double booking and enforces a 72-hour change rule.
P21 [List Paragraph] Replace manual counters with QR appointment passes and a webcam check-in desk.
P22 [List Paragraph] Support citizens without accounts or computer skills through SMS-verified walk-in booking and a support desk.
P23 [List Paragraph] Provide the director and administrator with oversight: dashboards, printing registers, staff and centre management.
P24 [List Paragraph] Protect personal data through verified accounts, hashed passwords, role-based access, audit records and data minimisation.

P27 [Heading 2] Scope and Limitations
P28 [Normal] In scope: the complete citizen journey from registration to document handover for NIC and passport applications (new, renewal and replacement), officer verification, biometric scheduling and check-in, walk-in and support services, notifications, administration and printing export.
P29 [Normal] Out of scope: a live payment gateway, fingerprint, photograph and signature capture hardware, real card or passport printing, native mobile applications and multi-language screens. Payments and biometric capture are simulated, and uploaded documents are stored on the server’s local disk.

P36 [Heading 2] Constraints and Assumptions
P37 [List Paragraph] The brief requires a Java web application built by the group within one semester; the system runs on JDK 17 or later with Microsoft SQL Server.
P38 [List Paragraph] Email codes use Gmail SMTP with an app password; SMS codes use an HTTP gateway on a team phone on the local network.
P39 [List Paragraph] Users need a modern browser; the QR scanner needs camera permission and works on localhost or HTTPS.
P40 [List Paragraph] Payments and biometric capture are simulated; mobile numbers use the Sri Lankan format and the interface is in English.
P41 [List Paragraph] Times use Sri Lanka time (Asia/Colombo); booking is open up to 90 days ahead and slots run from 8:00 AM to 6:00 PM.

P50 [Normal] The database identity_issuance_service on Microsoft SQL Server [8] has 25 tables and 33 foreign keys. Figures 3 and 4 were generated from the live schema; each box lists the primary key, foreign keys and the main columns. Three design decisions shape the model:
P51 [List Paragraph] Specialisation by shared primary key. CitizenAccount and StaffAccount extend UserAccount, and NICApplication and PassportApplication extend Application, so common data is stored once.
P52 [List Paragraph] Constraints in the database. Reference numbers, emails, phone numbers and slot positions (centre, service, date, time) are unique, and status columns have check constraints.
P53 [List Paragraph] Audit tables. ApplicationReview, AppointmentCheckIn, BiometricCollection, Payment and DirectorReviewReferral keep who did what and when.

P67 [Heading 2] System Architecture
P68 [Normal] LankaID is a layered monolith. Browsers request server-rendered pages from Spring MVC controllers; controllers check the session role and call transactional services; services use repositories to reach SQL Server and call outside systems when needed. The code is organised in eleven module packages, each with its own controller, service, model, repository and DTO folders.

P75 [Heading 2] Testing
P76 [Normal] The project has 324 automated test methods in 64 test classes using JUnit 5 and Spring Test [16]. Controller tests use MockMvc with mocked services; integration tests run real services against SQL Server inside transactions that roll back. They cover registration and OTP rules, the application workflow, officer decisions, payments, walk-in booking, booking changes and role access. The 85 biometric, booking, walk-in, payment and route tests were re-run after the latest hardening and all passed.

P89 [Heading 1] Project Management
P90 [Heading 2] Agile Approach and Sprint Summary
P91 [Normal] The team used Scrum [21] with a product backlog of 31 user stories (20 high, 10 medium and 1 low priority) written for five personas. The Identity Service Director acted as product owner and the IT project lead as Scrum master; the five developers formed the development team. Sprints followed the priority order, so every high-priority story was planned before any medium-priority story [7].
P92 [Normal] 
P93 [Normal] All sprint goals are met in the delivered prototype. Story PBI-14 (monitor system activity) is covered through audit records of reviews, check-ins and collections and through the director’s officer-performance and tracking views; a separate log browser was not built. The team also added items beyond the backlog during integration: director referrals, public announcements, the landing-page assistant and a citizen notification dropdown.

P97 [Heading 1] Conclusion and Future Work
P98 [Heading 2] Summary of Achievements
P99 [Normal] LankaID delivers the full identity-issuing journey in one portal. Citizens register with two verified channels, apply, upload evidence, pay, book a biometric slot and receive a QR pass; officers verify applications and run a webcam check-in desk; the director issues approved documents through a printing register; walk-in visitors and the support desk cover people who cannot use the portal; and the administrator controls staff, centres, fees and announcements. The prototype covers the product backlog, runs on 11 module packages with about 18,800 lines of Java and 6,100 lines of templates, and is protected by an automated test suite.
P100 [Heading 2] Challenges Faced
P101 [List Paragraph] Database drift. Hibernate validates the schema at start-up, so each member’s local database had to match the code. The team wrote migration scripts, a schema snapshot and a setup guide so teammates could bring databases up to date.
P102 [List Paragraph] Concurrent bookings. Two citizens could take the last slot place, or a slot could be closed during a booking. Row locking, version numbers and friendly conflict messages were added and tested.
P103 [List Paragraph] Parallel development. Five members worked on separate branches (240 commits, 37 merges), which caused merge conflicts and inconsistent interfaces until a shared theme and shared form-token and navigation components were adopted.
P104 [List Paragraph] External services. Email codes need a Gmail app password and SMS codes depend on a phone gateway on the local network, so these were hidden behind interfaces and replaced by mocks in tests.
P105 [List Paragraph] Time rules. Booking windows, the 72-hour rule and check-in dates depend on the server clock, so the application now fixes its time zone to Sri Lanka time.
P106 [Heading 2] Suggestions for Improvement
P107 [List Paragraph] Replace the simulated payment with a certified gateway and move uploaded documents to encrypted object storage.
P108 [List Paragraph] Integrate certified biometric capture devices and add automatic extraction of data from scanned certificates.
P109 [List Paragraph] Adopt a migration tool such as Flyway and add full framework-level CSRF protection.
P110 [List Paragraph] Page and index the officer history lists and run load tests before real use.
P111 [List Paragraph] Offer Sinhala and Tamil interfaces, an accessibility audit and a mobile application with digital credentials.
P112 [List Paragraph] Add threaded replies for support requests and email or SMS reminders before appointments.

TABLE 3
Quality | How the system addresses it
Security | Passwords are salted with BCrypt [2] (8–72 characters with upper case, lower case, digit and symbol). Every request checks the session role; state-changing forms carry session-bound tokens and booking changes use one-time confirmation tokens. OTP codes expire (email 10 min, SMS 3 min) with 5 attempts and a 60-second resend delay, following OWASP ASVS guidance [3].
Privacy | Only needed data is collected. No raw biometric data and no card numbers are stored, and QR passes hold only the appointment reference. Handling is aligned with the Personal Data Protection Act [4].
Data integrity and audit | Slot rows are locked while booking so the last place cannot be taken twice; bookings carry a version number; the schema has 33 foreign keys plus unique and check constraints. Review decisions, check-ins, biometric collections, referrals and payments store the staff identifier and a timestamp.
Reliability and performance | Business operations are transactional. Conflicting saves show a friendly “reload and try again” message, and maintenance mode can pause the portal with a public notice. Pages are server-rendered with indexed lookups; no formal load testing was carried out.
Usability and accessibility | Responsive layout, one consistent theme, inline validation messages, printable passes, a mobile menu and a status timeline; readable type, contrast, labelled controls and visible focus states aim at WCAG 2.2 [5]. The walk-in service covers citizens who cannot use the portal.
Maintainability | Layered packages per module (controller, service, repository, model, DTO), constructor injection, a Maven build, and 324 automated tests across 64 test classes.
